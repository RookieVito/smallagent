# 智能旅行助手 V0 阶段文档设计

## 背景

当前仓库已有项目企划文档 [智能旅行助手.md](/home/xia/Agent/智能旅行助手.md)，并提供了 [模仿/0_模板说明.md](/home/xia/Agent/模仿/0_模板说明.md) 作为“索引页 + 详细设计”渐进式披露示例。本次工作不是照搬示例的固定数量或命名，而是参考其分层思想，在 [阶段](/home/xia/Agent/阶段) 目录下为“智能旅行助手”设计一套更贴合项目实际范围的 V0 文档。

项目技术约束已经确定为：

- `langchain==1.2.15`
- `langgraph==1.1.8`

## 目标

在 [阶段](/home/xia/Agent/阶段) 下创建一套面向“前后端完整闭环”的 V0 阶段文档，使读者能够从索引页逐步进入 5 篇设计文档，并基于这些文档理解：

- V0 的用户输入与规划结果最小契约
- LangGraph 编排工作流的最小责任边界
- 前端展示与基础编辑的最小交互边界
- 外部服务依赖与降级边界
- V0 的验收范围与明确非目标

这套文档的目标是约束“最小可运行闭环”，不是展开所有实现细节，也不是覆盖后续阶段的全部能力。

## 已确认范围

本次 V0 的覆盖范围已经确认如下：

- 覆盖层级：前后端完整闭环
- 能力边界：`生成 + 展示 + 基础编辑`
- 不纳入 V0 验收：导出能力

其中“基础编辑”只指低风险、局部性的行程调整能力，例如：

- 删除景点
- 调整同一天内景点顺序
- 保存修改并刷新展示结果

以下能力明确不作为 V0 的必选验收项：

- PDF 导出
- 图片导出
- 多城市复杂规划
- 持久化与账号体系
- 复杂协同编辑
- 为地图导出兼容性提供最终方案

## 设计原则

### 1. 模板是参考，不是固定标准

[模仿/0_模板说明.md](/home/xia/Agent/模仿/0_模板说明.md) 只提供分层方式和最小契约写法的参考，不要求新项目必须采用相同的文档数量、完全相同的分组、或完全一致的命名。

### 2. 索引页只负责控制阅读扩展

索引页只回答“下一步应该看哪篇文档”，不重复展开设计正文，不承担契约定义责任。

### 3. 设计文档只负责最小契约

设计文档应优先定义输入、输出、边界、验收与依赖关系，不提前写实现教程、部署步骤、测试计划或完整 prompt。

### 4. V0 先锁定最小闭环

文档要服务“最小可运行闭环”，而不是一次性把整章企划里的全部功能都纳入 V0。任何容易显著扩大范围的能力，必须先在文档中被标记为非目标或后续阶段内容。

## 各文档职责

### 1. `trip-request-and-plan-contract.md`

职责：

- 定义 `TripPlanRequest` 的最小输入字段集合
- 定义 `TripPlan` 的最小输出字段集合
- 约束前后端共享的数据形状

它负责回答：

- 用户至少要提供什么信息，系统才能开始生成旅行计划
- 前端要拿到哪些结构化结果，才能完成展示与基础编辑

它不负责回答：

- 这些数据是通过哪些编排节点生成的
- 某个字段由哪个外部 API 提供

### 2. `planner-workflow-and-state-contract.md`

职责：

- 定义基于 `langchain==1.2.15` 与 `langgraph==1.1.8` 的 V0 工作流边界
- 说明规划流程中的关键节点、共享状态与最终合并方式
- 约束“景点检索、天气查询、酒店推荐、规划整合”之间的责任分工

它负责回答：

- 工作流最少包含哪些步骤
- 节点之间传递什么状态
- 谁负责输出最终 `TripPlan`

它不负责回答：

- 具体 prompt 文本
- 具体代码文件怎么组织

### 3. `frontend-experience-and-editing-contract.md`

职责：

- 定义前端 V0 的最小页面闭环与交互边界
- 约束“生成、展示、基础编辑”这三类用户能力
- 约束结果页展示必须依赖的最小数据

它负责回答：

- 首页最小输入表单需要覆盖哪些字段
- 结果页至少要展示哪些板块
- 基础编辑允许哪些操作，不允许哪些操作

它不负责回答：

- 具体组件库选型细节
- 动画、视觉设计和最终样式稿

### 4. `external-service-boundary.md`

职责：

- 定义 LLM、高德地图类服务、图片增强能力等外部依赖在 V0 中的边界
- 区分主流程必需依赖与可降级依赖
- 明确哪些失败会阻断主链路，哪些失败可以退化处理

它负责回答：

- 什么依赖属于规划主链路
- 什么依赖只属于结果增强
- V0 对外部服务的失败容忍度如何定义

它不负责回答：

- 各平台 API 的完整参数表
- 每个服务的部署或注册教程

### 5. `v0-acceptance-and-non-goals.md`

职责：

- 汇总 V0 的统一验收边界
- 固化 V0 明确不做的内容
- 防止其他文档在局部说明中悄悄扩 scope

它负责回答：

- 什么结果可以算作 V0 通过
- 哪些能力必须延后到后续阶段

它不负责回答：

- 数据字段细节
- 工作流节点细节
- 页面具体实现细节

## 写作约束

### 设计文档格式

每篇设计文档默认使用以下五段：

- `目标`
- `范围与非目标`
- `核心契约`
- `验收口径`
- `依赖与边界`

只有当文档明确依赖特定实现栈时，才额外加 `技术栈` 段。预计 `planner-workflow-and-state-contract.md` 会明确提到 `langchain==1.2.15` 与 `langgraph==1.1.8`。

### 链接规则

- 项目内跳转使用相对路径
- 文档正文不依赖机器本地绝对路径
- 索引页只链接到设计文档，不在索引页内复制正文

### 内容边界

本轮文档创建不应写入以下内容：

- 详细代码实现
- 完整 API 设计文档
- 环境变量清单
- 安装与部署步骤
- 测试计划和 TDD 任务分解
- 导出功能的兼容性实现方案

## 验收标准

当以下条件同时满足时，说明这份设计可以进入后续实现阶段：

- [阶段](/home/xia/Agent/阶段) 下的 V0 文档结构能够体现渐进式披露
- 两张索引页能把 5 篇设计文档分成清晰的两条阅读主线
- 5 篇设计文档各自职责单一，没有重复定义同一组契约
- V0 的能力边界被明确固定为“生成 + 展示 + 基础编辑”
- 导出能力被明确排除在 V0 验收之外
- 文档内容不依赖尚未确认的实现细节

## 实施后的预期结果

完成本次文档创建后，仓库中应新增一套可直接阅读的 V0 阶段文档，供后续实现、计划编写和阶段推进使用。该套文档将作为“智能旅行助手”在当前仓库中的第一阶段正式口径，但不取代后续更高阶段对导出、复杂编辑或更强规划能力的扩展设计。
